### Design constraint locked by Sir
- The new bot is MAKER-ONLY, post-only limit orders, never a taker. Budget: low hundreds/mo, not thousands.
- Speed reframe (critical): a taker races to HIT a stale quote; a MAKER races to CANCEL + REPRICE its OWN stale quote before an informed taker hits it. The hot path = tweet lands -> recompute fair value -> cancel affected resting quotes + re-quote first (capture the spread as the crowd catches up). NOT fast entry.
- Adverse selection is the #1 maker risk: you get filled exactly when you are wrong (informed taker lifts your stale offer the instant a tweet lands). Cancel/widen fast around tweet events.
- Fill-rate reality check: maker orders fill only when someone crosses to you; in thin tweet books you may rest and never fill. Measure real fill rate before scaling.
- Revenue: maker rebate (~10-12 bps/fill) + LP reward (rest near mid); maker pays ZERO exchange fee under V2. Treat rebate+LP as a primary revenue line.

### Verified Polymarket CLOB V2 execution specs (confirmed vs official docs 2026-07-01)
- CLOB V2 live 2026-04-28. EIP-712 EXCHANGE domain version = "2"; AUTH ClobAuthDomain stays "1". Nonce removed -> millisecond timestamp for uniqueness. Sign V1 -> order_version_mismatch (hard reject).
- Collateral = pUSD (Polygon ERC-20, 1:1 USDC); wrap USDC.e via the Collateral Onramp. V2 Exchange = 0xE111180000d2663C0091e4f400237545B87B996B; V2 Neg-Risk = 0xe2222d279d744050d28e00520010520000310F59 (one-time approve both for pUSD + ERC-1155).
- post_only boolean: would-cross -> INVALID_POST_ONLY_ORDER (never takes); with FOK/FAK -> INVALID_POST_ONLY_ORDER_TYPE; GTC/GTD only. Native mode for us.
- Heartbeat: send every 5s (field heartbeat_id, empty on first); no valid heartbeat within 10s (+5s buffer) = ALL open orders cancelled. Mandatory (whole book rests).
- 250ms taker delay: ONLY selected crypto/finance up-down markets (since 2026-06-05), NOT tweet markets, and irrelevant to us (never take). GTD expiration = now + 60 + N seconds.

### Architecture (two axes of isolation, two speed lanes)
- Vertical layers each its own process/failure domain: ingestion, brain, strategy modules, risk gate, execution, observability. Horizontal modules sealed, zero cross-imports, shared math in api/modules/shared/.
- Supabase = the message bus + persistence, but stays OFF the hot path. Hot path is in-memory in ONE process; DB only on the slow path.
- HOT PATH sub-second (tweet -> reprice -> cancel/re-quote). SLOW PATH every 5 min (discovery, pacing recalibration, exits, copytrader poll, full risk sync).
- Split risk gate: hot path = fast in-memory check (breaker off? within cached cap? price sane?); slow path = full 15-check recompute that caches its verdict. Always fail-closed.

### Backtest methodology (anti-look-ahead) - MANDATORY, checklist at `_DataMetricPulls/pacing_backtest/BACKTEST_RULES.md`

Leave-one-out is NOT walk-forward (ok for research, not live-accuracy claims). Correct idioms already in repo: priors = [p for p in sel if p['e'] < s]; diurnal/seasonal from posts before s; inputs obs(s,cps) + price_at(cps).

## Working Strategies (validated)

### Core edge: pacing as the brain, not the trade
- The market out-forecasts every pacing model at every horizon (crowd Brier ~0.10 at T-1h vs best model ~0.41), so do NOT build the bot to out-predict the count and wait for convergence. Slow-forecast convergence is DEAD.
- Best forecasting model is Kalman (11.9% mean abs count error on 113 walk-forward auctions), used as fair-value/brain only. Linear pace ties it (12.1%, single closest 25/113). Drop Hawkes (M2/M3 166-186% error), NegBin (M5 45-85%), and the old CurBayes (14.6%) from a new build.
- Pacing accuracy is only ~48% (coin flip) at the 0.65 entry checkpoint but hits 80%+ argmax at the 0.95 checkpoint (last ~2h of a 2-day auction); within-1-bracket accuracy is 94.4% at >=0.85. Calibrated pace-projection beats market argmax ONLY on 2-day Elon at mid-auction (77% vs 55%); it loses on 7-day and early entry.
- Bracket-probability model MUST floor already-passed brackets to 0% (any bracket whose upper bound < current observed count is impossible since count only rises), renormalize, and shrink projection variance as the auction ends (std *= sqrt(remaining_days/total_days)). Late-week (remaining_frac < 0.30) drop the right-skewed Negative Binomial component for a pure normal, else the model projects a winner below its own mean.
- Pacing math: Bayesian Gamma-Poisson blend, posterior = (prior_precision*prior_mean + obs_precision*obs_proj)/(prior_precision+obs_precision); obs_proj = total/elapsed_fraction; prior = mean/std of prior CLOSED auctions of same handle+duration; elapsed floored 0.001, ceiled 0.99. Beats naive linear extrapolation (5 tweets in hour 1 predicts 840/week).
- Regime persistence is the single biggest pacing edge: anchor early on a recent ~6-day baseline (corr to final +0.63; day-to-day autocorrelation 0.36). Within-window pace shape is near-efficient; last-6h momentum is NOT the edge.

### Auction mechanics (get these exactly right)
- Tweet-count auctions run noon-ET to noon-ET, EXCLUSIVE end at exactly 12:00:00 PM ET (2-day = 48h, 7-day = 168h). Resolution source is xtracker.polymarket.com only; MuskMeter does not govern.
- Counting rule: main-feed posts + quote posts + reposts/ReTruths count; pure replies (text starting with `@`) do NOT count. Elon has an extra "no community reposts" nuance text alone cannot detect; reposts identified by `RT @`. No per-post cap.
- Validated priors for projection: Elon 7-day ~207 (std ~55, n=22); Elon monthly ~1139 mean but median 923 (Dec 2025 = 1654 outlier) so prefer MEDIAN to dampen.

### Spike Trading (cheap-tail lottery, hold-to-resolution, live module)

The old 0.3c/0.5c/2c/5c/12c ladder is DEAD: every tier snapped to the 1c tick and was sized at $0.15, below the $1 CLOB min, so it never filled.
- All tiers clear Polymarket's order minimums: >=5 shares, >=$1 notional, price on the 1c (or 0.001 neg-risk) tick; size = round(notional_usd / limit_price). Entry window = first 24h of a 2-day auction only; unfilled tiers cancel after 24h.
- Widen the top tier 15c -> 22c when the PRIOR same-handle 2-day auction settled in a >=40 bracket (<40 lost), since baseline pace is structurally elevated. Resolve via auction_archive most-recent resolved (handle, window_days=2).
- Pre-ladder guard: do NOT enter when current price has already collapsed to the floor (neg-risk floor 0.001). Bug it fixes: floor price -> size = $3/0.001 = 3000 shares, kelly_pct=3.0, all rejected by the 0.15 cap. Compute kelly_pct = (size*limit_price)/bankroll (real dollar exposure), never size/1000.

  - HOLD-LIGHT: <=10 tweets AND >=18h left, or projected <=30% of cap.

ALL alpha is from harvesting intra-auction oscillation, NOT bracket wins (only ~1.9-5.6% of <40 auctions resolve YES). ### Sizing and risk gates
- Kelly is the sizing layer, not an edge source; it cannot rescue zero/negative edge. EV per share = P_win - p (a 20%-likely bracket at 10c is +EV). Kelly fraction f* = (q-p)/(1-p); use fractional (quarter-Kelly) plus a hard ~10% per-bracket cap. A small one-bet-per-auction edge (~200/yr) needs decades to converge; only high-frequency plays clear the Law of Large Numbers.
- Kelly BUY gate lowered from 0.01 (1% bankroll) to 0.001 (0.1%) so high-edge cheap brackets on 15-bracket auctions (each ~3-5% prob, ~3c edge, Kelly 0.2-0.5%) stop auto-PASSing. Safety holds: risk_manager min_edge_threshold (default 2%) plus depth_adjusted_size and portfolio caps trim downstream.
- Aggregate price ceiling is the biggest multi-bracket edge: cap the SUM of avg_prices across all brackets held in one auction at 0.65 (default). Sum < 1.00 means at least one held bracket must win; sum < 0.65 locks >=0.35 guaranteed edge per equal share. Modules may only go stricter via min(meta, floor).
- Treat same-auction brackets as a basket, not correlated risk: brackets are mutually exclusive and only one wins, so a correlated-exposure gate that caps "all brackets in same auction" will silently block multi-bracket buys and blunt the Kelly-gate fix. Re-audit / delete never-fired gates.
- Backtest on REAL HF fill prices, never assumed/constant entry prices. Constant-price backtests produced fake +133-148% results; with real fills the naive project-then-pick baseline is -76% ROI on Elon 2-day (Polymarket is efficient at the 0.65 checkpoint).

### Maker rebates (free money on every resting order)
- Polymarket pays two stacking maker incentives: a maker REBATE (per-fill, distance-from-mid agnostic, ~10-12 bps) and an LP REWARD (resting orders, weighted by proximity to mid). Real sample: $29.33 = $19.64 rebate + $9.68 LP. Place limit (maker) orders; park exit ladders early near mid to earn both. Cheap lottery bids far from mid earn ~$0 LP (fine, the thesis is moonshot return). MAKER = limit resting below ask / above bid; TAKER = market or limit-at-ask, no rebate.

### Surviving forward-only edges (need live L2, cannot backtest)
- Three candidate edges survive and require live order-book data: (1) structural/complete-set arb (buy all brackets when ask-sum < $1, riskless, model-free, the only confirmed riskless edge); (2) forensic finish-line (deletion-under-5-min, xTracker oracle lag vs live count, boundary precision near expiry); (3) speed/overreaction (the market provably reacts 4.75x larger on tweet-minutes, but at 1-min resolution the move CONTINUES 58% of the time, so any snapback edge lives in sub-minute ticks). Estimated ~15% chance speed becomes a real captured edge, but the recorder is nearly free and the same tick data sharpens the fair-value model, so it is +EV to run.
- Highest-upside direction: stop beating the market's forecast, reverse-engineer it. Fit thousands of price snapshots at (count-so-far, time-left) to recover the market's implied rate + uncertainty; "flip points" (a tweet flipping the favorite bracket) pin its sensitivity. Yields a fair value better than any model plus an overreaction detector. The whole pacing/recorder/EV machine is figure-agnostic and transfers to any countable, timestamped, bracketed market with repricing lag (tweet counts, sports totals, weather counts, box office).

## New Bot - Architecture & Structure

### Module isolation (the load-bearing rule)
- Each trading module is a self-contained package at `api/modules/<name>/` with these files: `module.py` (BaseModule subclass, entry point), `data.py`, `decision.py`, `module_config.py`, `__init__.py`. Optional `executor.py` per module.
- ZERO cross-module imports. Never `from api.modules.<other> import X`. The old bot's `elon_tweets` imported pacing/signals/regime/hawkes/projection from `truth_social`, so editing Trump's math broke Elon. Build with `shared/` from day one.
- All shared, pure-function math lives in `api/modules/shared/`: `pacing.py`, `signals.py`, `regime.py`, `hawkes.py`, `projection.py`, `enhanced_pacing.py`, `news_classifier.py`, `news.py`. These are I/O-free and were moved with zero logic changes against 64 passing tests.
- The Polymarket data client goes in `api/modules/shared/polymarket.py`, never inside a module. ~24 generic functions take handle/slug params: `fetch_active_tracking`, `fetch_xtracker_stats`, `fetch_xtracker_posts`, `fetch_market_prices`, `fetch_bracket_token_ids`, `fetch_order_books_for_brackets`, `fetch_order_book`, `fetch_market_volumes`, `fetch_wallet_history`, `normalize_bracket`, `fetch_market_brackets`, plus constants `XTRACKER_BASE`/`GAMMA_BASE`/`CLOB_BASE`/`RATE_LIMITS`/`BRACKET_ALIASES`. Add a `platform` param ('truthsocial' vs 'x') to `_fetch_trackings_raw` and propagate through every caller.
- Engine and routers must NEVER hardcode module names or handles. Real violations that caused silent failures: `ElonTweetsModule` hardcoding `name='Elon Tweets'` DB lookup (rename = silent empty signals); `routers/modules.py` hardcoding `name=='Truth Social Posts'`; `position_manager.py` with 115 lines of Spike-specific writes inside a generic service; `data_explorer.py` with 8 hardcoded handle if/elif branches; `bracket_stats.py` hardcoding `strategy=='spike_trading'`. Expose behavior via BaseModule methods/flags instead (e.g. `get_buy_order_ttl_hours()`, `auction_slug_patterns`, `divergence_card_enabled`).

### BaseModule API + module registry
- Override these per module: `get_handle`, `get_platform`, `get_config`, `save_config`, `get_display_keywords`, `get_auction_title_filter`, `get_auction_window_days`, `get_config_schema`, `supports_direct_post_count`.
- `get_config_schema()` returns field descriptors (key/label/type/min/max/step/help/section) that drive a schema-driven `DynamicConfigForm`, auto-generating editable config UI with zero frontend work per new module.
- Modules auto-register via `pkgutil.iter_modules` in `ModuleRegistry.discover()` over `api/modules/`. The engine never imports modules to register them; no `engine.py` edit is needed to add one. Specs saying "add an import line to engine.py" are stale, skip them.
- `registry.for_db_row(supabase_row)` maps a DB `modules` row to a module instance, matching the `strategy` field BEFORE keyword (so "Spike Rider - Elon" does not wrongly resolve to elon via the 'elon' keyword). `for_db_row()` matches on `display_keywords`; a missing override caused "Spike Trading" (name has a space) to fail matching the `spike_trading` keyword.
- Adding a module is drop-in: create the folder, implement BaseModule, registry auto-discovers, no engine/router edits. Verify via smoke test that the registry picks it up.

### When cloning/duplicating a strategy

### Bankroll, sizing + risk
- FOOTGUN: per-module risk/exposure caps compute off the GLOBAL bankroll setting in `api/config.py` (default $1000), NOT the `modules.budget` column. `per_trade_cap_pct=1.0%` on $1000 = $10 max bid; `per_wallet_cap_pct=5.0%` = $50. The `modules.budget` column is UI-display only unless wired into sizing math. In the new design, make `budget` actually bound sizing.
- Position sizing = fractional Kelly: `edge = model_prob - market_price`, full Kelly scaled to 0.25x, then reduced by regime volatility (TRANSITION -> 10% Kelly, high vol 15-20%), time decay (after 70% elapsed shrinks), and depth (never >30% of order-book depth). Hard cap 15% of bankroll per position. Only BUY if sized Kelly > 1%.
- Bracket sizing flow to reuse: project total -> model prob per bracket -> EV vs market price -> fractional Kelly stake capped at max-bet %. Live Elon table outputs Yes Price, Model Prob, EV, Max Bid (fair value), Kelly frac, Stake $, Shares per bracket. Config: Kelly fraction 0.25x, max bet 10% of balance. Note: % cells store 25/10 as raw text needing /100 conversion to 0.25/0.10.
- Spread-tolerance gating is correct discipline: find edge on illiquid tail brackets but refuse to trade empty books. `slippage_tolerance` is per-module config. Edge below threshold + wide spread still nets a loss (4% edge - 5% spread = -1%).
- ALWAYS limit orders, never market. Every order specifies a price.

### Engine loop + auction discovery
- Engine cadence: 5-min cycles (sync P&L + circuit breaker, exit check, then per-module evaluate -> signals -> risk approval -> paper/live executor), 30-min resolution check, 1-hr new-auction scan, 6-hr walk-forward recalibration.
- Auction slugs auto-discover every cycle via xTracker (`/api/users/{handle}/trackings`); the stored `market_slug` is a seed only, not used at runtime. Find the auction whose date range contains now and extract the slug dynamically.
- AUCTION-SELECTION BUG to avoid: `fetch_active_tracking` sorts by `startDate` ASCENDING and picks the earliest start = MOST-elapsed auction. A spike/early-entry strategy needs the FRESHEST auction (latest start, least elapsed). There can be 4+ concurrent Elon auctions (weekly, mid-week, new, monthly). New bot: fetch ALL active candidates and select by strategy intent, not the first match.

### Forecasting/pacing brain
- 5-model pacing ensemble: Regular Pace, Bayesian Pace, DOW-Hourly Bayesian, Historical Mean, Hawkes Process. Weights shift by elapsed_pct and regime: early favors Historical Mean / Bayesian, late favors DOW-Hourly + Hawkes. Outputs a probability distribution across brackets. Optional 6th model from cached parquet price patterns.
- Bracket selection ranks by `edge x sqrt(liquidity) x confidence`, picks top 3, with cross-bracket arbitrage (mispriced probability mass between brackets) and contrarian fade of brackets with >2x avg volume.
- KEEP the PACING_SPEC sigma fix, DROP the rest. `sigma = sqrt(max(mu - posts_so_far, 1)) * 1.5 + floor` dropped near-resolution Brier from a buggy 0.41 to 0.13 (old `sigma = MAX(mu*0.25, 8)` was ~10x too wide near close). Every other added layer (L4 clock, L4.5 up-only multipliers 1.15x morning/1.10x reply, L6 gate that freezes on posts_so_far) increases count error. The market is still sharper at every horizon (market Brier 0.049 vs model 0.13 at T-1h), so this is a good brain, not a trading edge.
- Reality check on forecasting edge: bracket hit-rate is a finish-line phenomenon. 7-day: ~22-25% at 2d out, ~41-45% at 24h, ~78-80% at 1h. 2-day: ~40-46% at 24h, ~90-94% at 1h. A 26-box market means random ~4%, so ~41% is ~10x chance but still not a trading edge. Grade models at fixed horizons (T-2d open + T-1d), not at the buzzer.
- `PACING_SPEC.md` (at `_DataMetricPulls/elon_schedule_analysis/`, mirrored in the `_PacingSpecs` sheet tab) is the single-source-of-truth contract: Layers 0-6, 9 signals A-I (A+F+G = shape estimate, B+C+E = gate, D+H = display, I = guard), session-break calibrated to 90 min. Implement the same layer definitions so Python projections match the sheet.

### Live L2 Recorder (the single most important fast-build move)

- **No historical L2 order-book data exists beyond ~2 months; it is irreplaceable and cannot be backfilled.** Trades are permanent on-chain events (2+ years), but order books are ephemeral state nobody archived (not in HF, not on GitHub). Canonical prices are hourly OHLC only with mostly-zero depth proxies; no L2 depth before ~Mar 2026. Build a forward L2 recorder NOW: every day not recording is edge permanently lost. Need ~15-25 logged markets (3-6 weeks) before any fill-exact P&L is trustworthy.
- **Recorder source:** Polymarket CLOB WebSocket `wss://ws-subscriptions-clob.polymarket.com/ws/market` streams full L2 book snapshots + every top-of-book `price_change` (best_bid/best_ask) + trades at millisecond resolution. A 45s test captured 1,369 messages incl 58 full book snapshots with 42 ask levels of real depth. Subscribe to BOTH YES and NO tokens per bracket (954 tokens). `price_change` events arrive batched under `price_changes[]`, each with its own `asset_id` + best_bid/best_ask. Complement check: bracket YES ask 0.001 / NO bid 0.999 sums to ~$1.
- **Storage schema:** ~98% of events are `price_change`. Raw-JSON-everything = ~9 GB/day for 37 markets. Store `price_change`/trades as tight typed columns (with `_f`/`_i` safe-parse helpers) and keep ONLY full-depth book snapshots as JSON: ~1.59-1.82 GB/day all-markets, ~0.5 GB/day Elon-only, full fidelity preserved. Write a self-describing `_tokenmap` alongside recordings.
- **Parquet cannot be appended** (index written at end of file). A 24/7 recorder must write incremental sealed chunks every 30s (~2,880/day) so a crash loses at most 30s, then compact a day's chunks into one clean file per market type (7-day, 2-day, monthly) at pull time.
- **Six hardening fixes a 90s test will NOT surface, required before 24/7 run:** (1) `run_forever` RETURNS (not raises) on disconnect, resetting exponential backoff every loop = reconnect storm / IP-ban; gate the reset on a min-alive duration (>30s session via on_open timestamp). (2) `flush()` swaps rows out of buffer BEFORE `to_parquet` so any write failure permanently drops data; snapshot (don't swap), write to temp + `os.replace` (atomic), `del` only written rows on success. (3) non-atomic parquet write leaves corrupt chunks; use temp+rename. (4) no SIGTERM handler so every Railway redeploy loses up to `FLUSH_SECONDS` (30s); CPython only handles SIGINT, add a signal handler/atexit. (5) no silent-stall watchdog (a half-open socket looks alive but captures nothing). (6) empty-discover exits + unbounded buffer on disk-full + no `OUT_DIR` retention (~48 GB/mo on a fixed volume = guaranteed ENOSPC); add retention/offload.

### Polling Cadence & New-Auction Speed

- **Split into two cadences:** new auctions need a ladder within ~60s, so run a 1-minute insta-buy scanner watching specifically for brand-new auctions alongside the 5-minute full evaluate cycle. Spike entries can land mid-auction (missing by 30 min = buying at $0.40 vs $0.05), so 5-min polling is the sweet spot; faster adds nothing because confirming a "sustained" spike already needs ~3h of post-spike data. Anchor/fade trades have a 0-12h window off a slow opening-price anchor, so a 15-min cron loses no edge. Run as two Railway crons: anchor `*/15`, spike `*/5`. Each run hits ~120 slugs in ~8s; ~29k requests/day total is within bounds.
- New-auction discovery asks the Gamma Series API (`elon-tweets-48h`) for every 2-day auction open now OR opening within a 7-day lookahead, so the bot sees a new auction the moment Polymarket lists it.

### Tweet Source / Speed Edge

- **xTracker lags real-time ~5-15 min; the X API v2 filtered stream is sub-1s but priced out** (Pro $5K/mo or Enterprise $42K+/mo as of Jan 2026). For Elon (single account) a third-party X scraper (~$20-50/mo) gives sub-second counts. For Trump, xTracker + CNN archive cover it; the CNN archive matches xTracker speed but returns raw posts so you can self-count and detect divergence.
- **Measure the tweet-to-price latency edge as T0 = real tweet post time to T1 = first bracket midpoint move >=15%**, NOT via xTracker import timestamps. The CLOB reacts to the X firehose/scrapers, not xTracker (the flawed xTracker-import-to-CLOB median of ~167s was correctly rejected). Canonical prices are hourly OHLC and hide sub-hour timing, so second-level lag requires either a live CLOB WebSocket subscriber + a fast tweet source running continuously, or a retroactive `data-api/trades` pull per spike.

### Truth Social Fetch (Trump)

- **Truth Social API is Mastodon-compatible and Cloudflare-protected.** Endpoint: `truthsocial.com/api/v1/accounts/{id}/statuses` (Trump `account_id` 107780257626128497, ~33k posts since Feb 2022; lookup via `/accounts/lookup?acct=`). Default `httpx` gets 403 on TLS fingerprint; `curl_cffi` profiles `chrome110`, `safari17_0`, `firefox133` return 200 while `chrome124`/`chrome120` are CF-flagged. Rotate profiles on 403/429; do NOT send an `Origin` header (triggers CF). Add `curl_cffi>=0.7.0`. Aggressive per-IP rate-limiting (banned after ~5 pages): use `since_id` incremental fetch, 5-15 min backoff, idempotent page-level checkpointing.
- **Railway runs on datacenter IPs Cloudflare blocks by reputation; a residential proxy is the real fix** (perfect TLS fingerprint alone still 403s). Set `TS_PROXY=http://user:pass@host:port` and the fetcher auto-uses it. IPRoyal cheapest (~$1.75/GB), low-volume polling ~$2-5/mo; Bright Data/Smartproxy/Oxylabs alternatives.

### Persistence (the data is the asset)

- **Persist raw post counts every cycle; never discard live fetches.** Write `post_count_snapshots` (`module_id, source` [`xtracker`|`truthsocial_direct`], `tracking_id, window_start/end, count, latest_post_at, error, raw_response` jsonb, `captured_at`) every 5 min for both sources, plus a `truth_social_posts` raw archive (full status jsonb) for window recomputation. UI can be rebuilt; 5-min snapshots cannot be backfilled.

### Sparse-Trade Price Reconstruction

- For sparse markets (some 2-day brackets get only ~50 trades), reconstruct the price timeline by binning trades into **30-min buckets relative to auction close** (T-48h to T-0h, not wall-clock), taking the median trade price per bucket and flagging empty buckets. Trading clusters in the final 24h. Note hit-rate (price traded there) is not fill-rate (could you fill $100 there); for $100 size usually fine. Order-book DEPTH at past timestamps is NOT in trade data, only executed prices, so use trade-derived proxies: spread = high-low in window, depth = summed trade size at price, fill-prob = fraction of minutes with a trade (~90% of what limit-order backtests need).

### Telegram Alerter (read-only, never trades)

- **Telegram is the live notification channel; the alerter is READ-ONLY and never places trades** (`@PolymarketActivitiesBot`). Account-activity watcher polls `data-api /activity` every 30s, tracks last-seen timestamp per event type to dedupe, classifies LIMIT BUY/SELL FILLED with maker / taker badge, P&L on sells, open-position-after-fill, auction time-left, plus a 9PM ET daily P&L summary. A separate P&L watcher (60s) fires only at fresh tier bands (+10/25/50/100/200%, -10/25/50/75%) with a 30-min cooldown and per-position last-alerted-tier in state (~5-6 alerts/position lifetime max). Smart triggers: auction-ending at T-2h, YES>=0.95 resolution-locked, YES<=0.03 position-dying, sibling bracket moved >25%/1hr.
- **Spike-alert cron must gate or it spams every historical spike** (first deploy fired 61 Slack alerts). Required gates: (1) spike occurred within last 4h of auction-time, (2) spike price >=$0.05, (3) `BASELINE_MODE` env var on first run silently populates the dedup state file without sending, (4) skip if `current_price` dropped below the pre-spike baseline (spike already unwound = stale alert).

### Backtest & Verify Tooling

- Build a reusable backtest engine (`backtest/engine.py`: `load_auctions`/`simulate_auction`/P&L, multi-handle Trump+Elon, multiple durations, stop-loss, late-buy gates, Kelly allocation, signal toggles) with a natural-language agent layer on top so plain-English ideas ("sell half at 1.5x across last 20 auctions") run in seconds without rewriting scripts. Run independent variations as parallel background tasks.
- Verify a refactor with no deploy/network: AST-parse every touched file, runtime-import `api.main` and all modules, walk the registry calling `get_handle()` on each, and run the test suite tracking the pre-existing-failure baseline (the old suite had 13 known failures on master, so a refactor that keeps it at 13 is proven clean).

## Build Learnings & Gotchas

### Engine cycle resilience (most common cause of silent multi-day outages)
- Wrap the ENTIRE cycle body in try/except + log the traceback. A single unhandled exception anywhere (including `_sync_risk_state`, `_run_exits`, `_check_data_freshness`, `_process_pending_signals`, registry iteration) kills the cycle for ALL modules permanently if unprotected. Found in `api/services/engine.py`.
- APScheduler hardening on the cycle job: `coalesce=True`, `misfire_grace_time=60`, plus a watchdog every 5 min that detects `_cycle_last_run_ts` older than 15 min.
- CRITICAL: re-registering a job on a dead APScheduler scheduler is a no-op. The watchdog's "job re-registered" does NOT revive a wedged scheduler thread. Recovery must be PROCESS-level (external supervision), not in-process re-add. Never trust an in-memory `_running=True` flag as liveness, it makes `engine.start()` a silent no-op.
- A data-freshness gate that BLOCKS the cycle when the latest decision log is stale will deadlock forever: stale gate prevents writing new decisions, which keeps data stale. Always write a decision-log heartbeat even on the stale-data path so the gate self-heals.
- Every module MUST override BaseModule's abstract contract (`get_handle`, `get_platform`, etc.) or it raises NotImplementedError every cycle. Handle-less modules (copy-trading style) return `''` and all engine helpers must skip empty handles instead of crashing.

### Live-trade safety (money path)
- NEVER mark a CLOB limit order `filled` on submission. The POST returns a submission ack, not a fill. Write `submitted` on live POST; only open/close positions after a fill-confirmation POLLER verifies the fill. The new bot needs this poller from day one.
- Live CLOB orders require the 256-bit ERC-1155 `token_id`, NOT the human bracket label. Populate `Signal.token_id` from `market['token1']`/`clobTokenIds` (handle JSON-string variant), store it on the positions row so exits can SELL, and make the live executor refuse any signal with no `token_id`. Thread it end-to-end: market fetch to Signal to order to position to exit.
- Exits (stop loss, trailing, take profit, edge reversal) must actually place a SELL order via the executor. Original `close_position()` only updated the Supabase row to `status=closed`, making all live exits no-ops. Only mark closed if the order actually fills.
- Exits must run UNCONDITIONALLY every cycle and BEFORE the circuit-breaker check. If the breaker trips and exits are gated behind it, a -30% stop can bleed to -50% during the cooldown.
- Route exit/SELL signals through the exit_manager, which BYPASSES entry-side gates (edge threshold, kelly, EV, spread, liquidity, settlement-decay) but still respects circuit breaker + paper_mode. Risk checks that compute notional as `kelly_pct * bankroll` must short-circuit for SELLs (`kelly_pct=1.0` means "liquidate 100% of THIS position", not "add 100% of bankroll"), or the bot can BUY but never SELL.
- Both executors must route SELL to `close_position()`/`partial_close_position()`, never `open_position()` (which created phantom positions on every SELL). Use an atomic claim (`update set status='closing' where id=? and status='open'`) to prevent double-sells; sweep stuck `closing` rows older than N min.
- Live trading requires a DUAL guard: `PAPER_MODE=false` AND `ENVIRONMENT=production`. `LiveExecutor` must raise `RuntimeError` if instantiated in paper or non-production. Validate `price in (0,1)` and `size>0` at the CLOB submission boundary.
- Persist circuit-breaker win/loss counters to the Supabase settings table and reload on boot; in-memory only resets every restart. Wire `record_win`/`record_loss` from the resolution tracker (they were dead/never called).
- All CLOB orders must be limit orders: `OrderArgs(token_id, price, size, side)`, defaults to GTC. PaperExecutor simulates fills at the limit price and never touches CLOB.
- Coordinate position-opening across executor profiles. A MultiExecutor that fans one Signal to N profiles in parallel threads double-spends every BUY (each profile independently calls `open_position()`). Never let profiles open independently.

### Risk-check correctness (fail-CLOSED)
- All risk checks fail CLOSED (block trading) on any DB error. Real bid-ask spread check (reject if `spread>slippage_tolerance` or no data), depth-based liquidity (reject if order `>30%` of book depth or no data), no empty stubs. Loss/drawdown checks must block until first PnL sync.
- Risk-sync must run at engine BOOT before the first cycle (pre-warm), not inside `_run_cycle`. On cold start, signals hit `risk_manager.check()` before `_risk_synced` flips True, so 100% get rejected with "risk state not synced" and zero orders place for hours. When `daily_pnl` is empty, treat as "no constraint" (0 losses), not "block all".
- Structural/non-ensemble strategies (edge=0, model_prob=0) get silently rejected by edge/EV/spread/liquidity gates. Add a `metadata['skip_edge_check']` flag that bypasses `_check_edge_threshold`, `_check_negative_ev_aggregate`, spread, and liquidity, while keeping the floor and all other checks for everyone else.
- `realized_pnl` on close must ACCUMULATE (`(existing or 0) + pnl`), never overwrite, or partial-fill P&L from earlier tranches is lost. Always write `closed_at = now` so P&L charts bucket by close date.
- Only persist a position row AFTER a confirmed fill. Cheap ladder tiers (0.3c/0.5c) almost never fill; a scratchpad row created at BUY-attempt time with `entry_size_shares=0` walks to MONITORING with 0 shares, then SELL fails with "No open BUY position". Skip SELL when `entry_size_shares<=0`. Add a DB unique partial index on `(module_id, market_id, bracket)` WHERE state IN ('WAITING','MONITORING') to block dup/race inserts.

### `/api/engine/stop` is a KILL SWITCH (not a pause)
- `/api/engine/stop` market-closes EVERY open position across modules at avg_price (realized_pnl=0). NEVER call it to restart a wedged cycle. Build a non-destructive `/api/engine/restart-cycle` (remove + re-add scheduler jobs without touching positions); to clear a wedged scheduler, do a process-level Railway redeploy. Protect `/stop` with JWT auth. Always grep the handler body before calling anything named stop/cancel/kill/reset/clear/delete/disable.
- Provide an explicit PAUSE that stops new entries but does NOT liquidate and keeps exits firing. A decorative `enabled=True` flag on BaseModule that the engine never reads is useless: if you want per-module pause, the engine MUST read the flag every cycle.

### Apply migrations BEFORE deploying code that references the table/column
- A missing table/column combined with a nested try/except silently drops writes for days while the bot looks alive. Examples: missing `pending_signals` (migration 006) dropped all deferred signals 4 days; missing `orders.metadata` column killed the BUY ladder silently. Gate any code referencing a new table/column behind the migration landing in prod first, and surface schema-cache errors loudly.
- Deploy the CODE fix BEFORE cleaning data. REST/SQL cleanups of duplicate rows do not hold if the deployed code still re-creates them every cycle. Order: deploy code fix, then clean data, then add a DB-level unique constraint as the hard backstop.

### Data sourcing: discovery, windows, counting
- Pull bracket lists and trades FRESH from Polymarket Gamma + data-api. NEVER use the old `whale_analysis` parquets (969 files), they are an incomplete scrape (~10 brackets captured vs ~17 actual) that silently demotes auctions to low-confidence and drops winning brackets. Clean pipeline: Gamma `/events?tag_id=972` (Tweet Markets; `tag_id=282`=Elon) paginate to discover auctions, read `event.markets` for brackets + conditionIds, then `data-api.polymarket.com/trades?market=<conditionId>` paged 500/trade at 0.5s rate limit. Authoritative Gamma counts: Elon 243 auctions, Trump 57.
- xTracker is the authoritative auction DISCOVERY source, not Gamma's paginated `/events` (which caps ~100k offset and hides `restricted:true` US-geo events). Enumerate via `xtracker.polymarket.com/api/users/<handle>/trackings`, reconstruct slugs from titles, validate each via the EXACT-slug endpoint `gamma-api.polymarket.com/events?slug=<exact-slug>` (returns restricted events the list omits).
- Auction windows are noon-ET to noon-ET (12 PM ET = 16:00 UTC during EDT). Parse the window from the MARKET date slug, never from canonical `auctions.start_utc/end_utc` (trade-derived, ~2x too wide) and never from Gamma `startDate` (the pre-market LISTING date, often days early or a mid-race add-on). Convert post timestamps UTC to ET via `zoneinfo.ZoneInfo('America/New_York')` and add days IN ET (167h spring-forward, 169h fall-back), never 168h UTC. `winning_bucket` is reliable for high/medium-confidence auctions.
- LOCKED Elon count rule: noon-ET window from market dates + originals + quotes + reposts + main-feed self-replies (`in_reply_to_user_id == 44196397`). EXCLUDE off-feed replies and community reposts. Reposts DO count (the old "exclude reposts" idea was a broken-OSINT artifact). Validates exact vs xTracker (126=126, 46=46), residual wobble +/-2-3 tweets (deleted tweets + boundary).
- xTracker is NOT the resolution oracle and frequently undercounts. Polymarket resolves via UMA optimistic oracle against the source site. Resolution hierarchy: UMA oracle (real resolver) > xTracker (PRIMARY predictive) > source site (SECONDARY, activate if xTracker doesn't update) > CNN archive (Trump cross-check). Truth Social source of truth = `truthsocial.com/api/v1/accounts/{id}/statuses` (Mastodon; Cloudflare blocks datacenter IPs, call from residential/Chrome). Trump count = main-feed posts + quotes + reposts; pure replies do NOT count.
- ALWAYS filter trades to `outcome=='Yes'` before any bracket price metric. Mixing YES and NO (same belief inverted across $0.50) corrupts every number and fakes spikes. Apply `df = df[df['outcome']=='Yes']` at the very top of any price/spike/grid computation.
- Brackets are per-auction data fetched from Gamma, NEVER module constants. Elon auctions have ~20-30 dynamic brackets (`<20` to `580+`) vs Trump's 11 (`0-19` to `200+`). Parse labels like `200-219`/`580+` into `(lo,hi)`; heuristic: `>11` Gamma markets means dynamic-bracket auction.
- Gamma fetchers MUST filter out resolved/closed brackets (`closed=True OR acceptingOrders=False`) or model probability dilutes across dead brackets and Kelly never clears the BUY gate (Elon monthly emitted 0 signals because ~29 resolved-NO brackets were ingested). Filter brackets, never skip the whole auction.
- Sort brackets numerically with a custom key (`<N` to a very-small number, else lower edge): `<40` first, `240+` last. Alphabetical puts `115-139` before `<40`. Centralize one `bracketSortKey`/`_bracket_lo` helper and filter to the CURRENT auction's grid so retired brackets don't surface.

### Order-book / fills
- Read bid/ask/spread from Gamma `bestBid`/`bestAsk`/`spread`, NOT the raw CLOB `/book` endpoint (returns near-empty on-chain books, e.g. bid 0.01/ask 0.99 = fake 0.998 spread, blocking every trade). `fetch_market_prices()` already pulls Gamma, just also extract those fields.
- Polymarket order book is OFF-CHAIN: no free historical L2 depth exists. All free datasets are trades/fills only. L2 depth exists only from a paid third party or by recording the live WebSocket forward. A buy limit is a price CEILING that fills cheapest asks first (price-time priority), not at your limit.
- Validate every order against all three CLOB minimums at signal-EMIT time (not just the executor): >=5 shares (`min_order_size=5` means shares, not dollars), >=$1 notional (server-enforced, NOT in Gamma metadata), price on the tick (1c standard, 0.001 neg-risk). Pre-emit MIN_PRICE_FLOOR=0.001 (CLOB minimum tick, not 0.01) + tick-snap before building signals.
- PaperExecutor must only fill a limit BUY when `best_ask <= limit price` (else return unfilled), never at current ask; falls back to filling at limit price only when real book data is unavailable. Handle `fill_price=None`/`unfilled` status in the engine.
- WebSocket: subscribe <=150 tokens per connection (use multiple connections). CLOB silently DROPS tokens when many are subscribed via multiple frames on one socket (~342 tokens dropped the 2-day chunk). Add a PER-SERIES watchdog (a whole-socket watchdog misses per-series drops because a busy stream keeps the socket looking alive).
- Trade exclusively via the CLOB API from the bot wallet, never the website. Orders carry a `builder` field for fee attribution; malicious browser extensions can stamp web-UI orders with their own builder address. API/bot-wallet trades are untouched.

### Async / scheduled jobs
- NEVER call `asyncio.new_event_loop()` or `asyncio.get_event_loop().run_until_complete()` inside FastAPI/uvicorn or APScheduler worker threads. Python 3.12+ does not auto-create a loop in non-main threads, so it raises RuntimeError, gets swallowed, and the job writes ZERO rows silently. Use `asyncio.run()` (or a `_run_async` helper) for blocking IO; do notifications fire-and-forget in a daemon thread so slow Slack POSTs don't freeze the cycle 10-20s and miss exit timing.
- NEVER put a blocking external HTTP call inline in a user-facing/pacing endpoint. Wrap supplemental fetches in `asyncio.wait_for(..., timeout=3.0)` and return `{count:null,error:'timeout'}` on timeout; supplemental data must never gate the core response.
- Wrap external data-source calls (xTracker/Gamma/CLOB) in a retry+cache helper: 3 attempts with exponential backoff (0.5/1/2s) on 5xx/timeout, then serve cached payload up to 60s old. A single transient 5xx must not cascade into trading/dashboard errors.

### Config / module isolation
- PUT config endpoints must MERGE incoming fields into the EXISTING stored config (`{**DEFAULT_CONFIG, **stored, **incoming}`), not into DEFAULT_CONFIG. Otherwise toggling one dashboard field silently resets every other field (including risk checks) to defaults.
- Each module owns its own config, exit thresholds, and health. Never load one module's config (e.g. Trump's `get_module_config`) for all modules; route through registry-resolved `module.get_config()`. Set `strategy` explicitly per module, never rely on display-name keyword matching. Make registry `discover()` idempotent and explicitly skip `shared/`.
- `shared/` code must NOT import from any specific module (circular dependency). Dependencies flow modules to shared, never shared to module. Self-resolve paths inside shared.
- Health/telemetry hooks fire AFTER the per-DB-row loop, not inside it. Spike has 2 rows sharing one class, so an in-loop hook fired health-record twice per cycle. Accumulate across rows, fire `_record_cycle`/`_persist_health` once after the loop.

### Observability (don't let it lie)
- Persist EVERY generated signal with an explicit status (generated/deferred/approved/rejected). Old bot only INSERTed rejected signals (approved ones were tagged via UPDATE during execution), so a 0-row signals table looked idle when it wasn't.
- Engine liveness/staleness must be measured by per-cycle `log_type='decision'` rows (fire every cycle), NOT the signals table (only written when a tradeable opportunity exists). A stale-data check must return False on real staleness (`age_hours > threshold`) with a distinct message for the DB-probe-failed case, not "return True except on exception" (which alerts on DB outages, not real staleness).
- NEVER use bare `try/except: pass` around DB writes for signals/orders, circuit-breaker `_persist_state`, or `_log_error`/`_log_rejection`. Silent swallowing hides production failures (signals table can stop while logs keep succeeding, looking dead). Add a `traceback` kwarg to `_log_error` and persist it in `logs.metadata`.
- Concurrent cycles race on pending-signal dedupe: on unique-violation the except must return True (already deferred), NOT False (which falls through to immediate execution at the pre-dip price). Catch the unique-violation specifically; make all dedupe fail-CLOSED.
- Health-state model: TRADING (trades in last 24h), CYCLING (cycles>0, trades=0, no errors), STUCK (errors>0 OR cycles=0), plus a one-line "why" (e.g. "QUIET regime shrinks Kelly below threshold"). Compute from real runtime state, separate from the DB `status='active'` flag which lies. Surface `/api/engine/health?module_id=X` PER-MODULE so one module's data-feed failure never paints another's page red. Gate the Degraded banner on 2+ errors in 15 min, label it "degraded" (amber) not "paused".

### Strategy gating (don't accidentally generate zero signals)
- Never let entry gate and time-decay windows overlap. `entry_gate_pct=0.75` + time-decay shrinking Kelly after 70% elapsed left only a 5% window that crushed size below the 0.01 threshold (0 signals ever). Fix: `entry_gate_pct=0` and floor time decay at 0.30 (`max(1.0-elapsed_pct, 0.3)`). Result: 0 to 51 signals first cycle. Cross-check that every gating-parameter combination leaves a viable window.
- Make all timing thresholds PERCENTAGE-based (not `elapsed_days<2`) so one code path handles 2-day, 7-day, and monthly auctions.
- Remove the `min_market_volume_24h` gate for limit BUYs (set to 0). Volume only matters on EXIT (handled by the SELL-NOW best_bid floor). A limit at 12c fills at 12c or not at all regardless of volume. Give spike BUY orders a 24h TTL, never the default 5-min sweep, so 0.5c limits aren't cancelled before they fill.
- Python falsy-zero bug: never use `x or default` for numeric fields where 0 is valid (`summary.get('days_remaining', 0) or fallback` returns the fallback when xTracker honestly returns 0 for a closed auction). Use explicit None checks; short-circuit projections for closed auctions to the locked running total.

### Backtest / projection math
- The decisive backtest is beating the MARKET PRICE, not point-prediction accuracy (pacing shape is efficient, so point accuracy ties naive). At each hour compare model bracket probabilities to market-implied price, bet only disagreements. Report locked-pair P&L separately from naked-leg P&L and the worst-5% naked-loss tail.
- Before trusting any auction backtest, validate the counted "actual" total lands in the bracket the market actually resolved on. One backtest graded models against a broken answer key (counted actual fell in the winning bracket only ~7% of 87 auctions). If the model's actual rarely lands in the winning bracket, the count basis is broken, fix it first.
- Bracket probability distribution must use sigma from REMAINING uncertainty, not total: `sigma = sqrt(max(projection - posts_so_far, 1))`, and zero out any bracket whose upper bound `< posts_so_far`. The old `sigma=max(projection*0.25, 8)` was ~10x too wide and leaked probability into already-passed brackets. When the lock/bedtime gate fires, collapse sigma to ~0.5 to peg odds ~100% on the bucket holding `posts_so_far`.
- Winner inference from last market price is unreliable (~89% wrong on Elon, the `<40` lottery bracket is the most-traded and its speculative trades fool a `last_price>=0.95` check). Derive the winning bracket from actual post counts in the ET window, or from Gamma `/events?slug=` where `outcomePrices=['1','0']` marks the YES winner (condition_id lookups fail; Gamma only indexes current/recent markets, slug works for all history).
- Spike detection must be directional + sustained + volume-filtered, never top-decile absolute delta (counts downward crashes as spikes; single-fill noise dominates). Rules that worked: >=3 trades/hour, 3-hour rolling smoothed price, upward jump >=+40%, prior baseline <$0.50, next 2 hours stay >=70% of spike price, skip first 4 settling hours, drop fills below $0.002-0.005 (clearance dumps).
- For schema-drifting markets (tweet counts re-bucketed over time), anchor to the LATEST auction's bucket set, include past auctions only if Jaccard overlap >=0.8, and filter the output grid to ONLY anchor-schema brackets. Detect "static" markets via Jaccard >=0.6 of label sets. Normalize whitespace label variants (`150-174` vs ` 150-174`) before counting.
- `auctions_seen` must increment once per auction the bracket appears in, independent of winner resolution, or undetermined-winner auctions get dropped from the denominator and `spike_frequency_pct` exceeds 100%.

### Frontend (dashboard cards)
- Confirm field names from the endpoint's OWN response builder before consuming. A card read `pacing.dow_hour_heatmap` as `d.count` but the builder emits `{dow, hour, avg, samples}`, so every cell was undefined and `v.toFixed(2)` white-screened the whole page. Guard every `.toFixed()`/`.toString()` with `Number.isFinite()` or `?? 0`.
- P&L curve final point = total realized + total unrealized summed across ALL brackets; reconcile to the KPI tiles (a per-bracket-realized / all-bracket-cost mismatch faked +808% while KPI showed -$175). Show $ primary, % secondary; count only BUY trades for cost basis; wallet-derived positions need a real `closed_at` (empty string `<= tradeTime` is always true in JS and corrupts the series).
- When a UI bug appears right after a merge, diff the FULL merge including BACKEND changes, not just frontend prop wiring (a backend blocking call, not a prop regression, caused empty dashboard cards).

### Credentials / environment
- The bot reads credentials from `PolyMarket_Bot/.env` (pydantic-settings `_env_file`), NOT `~/.credentials/shared.env`. Railway prod reads its own dashboard env vars (neither file). When changing wallet keys, update ALL of: local `.env`, Railway dashboard, and `shared.env`. A stale local `.env` would trade from the wrong wallet locally.
- Verify which wallet actually trades by on-chain positions/activity, never from memory; a key swap is a migration that can strand open positions, not a config typo. Polymarket cash lives in the off-chain proxy wallet (migrated to pUSD) and the public data-api `/value` + `/positions` report only positions, not idle cash, so a funded wallet can wrongly appear empty via API. Trust UI / CLOB auth (`get_api_keys` succeeding proves the wallet is real).

### Tooling / platform gotchas
- "Working" = a completed round-trip trade (signal emits to executor to fill to position to SELL to realized PnL on the LIVE instance), NOT a green code-only pipeline. AST/import/schema QA repeatedly passed while the bot silently didn't trade. Run the `/qa-real-trade` 6-step round-trip gate, not just `verify-bot` (which only exercises the module surface and never the risk_manager/executor pipeline).
- py_clob_client requires typed dataclasses, NOT dicts: `OrderArgs(token_id, price, size, side)` and `ApiCreds(api_key, api_secret, api_passphrase)`. A dict crashes later with AttributeError (`'dict' object has no attribute 'token_id'`) only after signal emission is unblocked.
